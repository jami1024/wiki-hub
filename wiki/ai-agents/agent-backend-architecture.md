# Agent 后端的三层架构：从循环到可维护系统

## 摘要

Agent 的基本循环容易实现，但把模型协议、对话存储和流程控制混在一起，会让更换实现和测试流程变得困难。Hucci写代码 用一个后端设计示例说明：先定义对话、工具、上下文等内部概念，再由应用层编排流程并声明所需接口，由适配层处理外部协议，最后在组装根接入具体实现。其设计价值在于把稳定的流程与可替换的实现分开；工具调用前增加模型审核，是这个示例采用的一项具体方案。

## 1. 先明确流程，才能看清哪些变化需要隔离

作者从一条完整的对话流程出发：收到用户消息后，把指令、可用工具和历史消息组织成上下文，发送给模型；如果模型请求调用工具，就审核并执行，再把结果交回模型，继续循环；没有工具调用或达到轮数上限时结束。过程中，每条消息产生时都持久化。来源：00:27–00:57。

这段流程本身并不复杂。问题出在直接把它和外部实现写在一起：从 OpenAI 协议换到 Anthropic 协议，可能要修改多处代码；测试流程时，也可能被迫真正调用模型。作者以这两个场景解释分层的动机——让流程便于维护和测试。来源：01:08–01:25。

因此，后续设计始终围绕两个问题展开：系统内部怎样表达这段流程，以及怎样使用外部服务而不让流程依赖具体实现。

## 2. 三层各有职责，接口让流程可以替换外部实现

作者按工作的性质划分三层：

| 层次 | 负责什么 | 示例 |
| --- | --- | --- |
| 领域层 | 定义系统内部使用的概念 | 对话 `session`、消息、工具 `tool`、上下文 `context` |
| 应用层 | 编排流程，声明流程需要的外部能力 | `agent_service`、`session_store` 接口、`model_client` 接口 |
| 适配层 | 在内部概念与外部协议之间转换 | JSONL 存储、模型客户端、HTTP 或 CLI 入口 |

来源：01:34–02:40、04:10–04:56、06:34–06:46、09:07–09:20。

以存储对话为例，系统内部关心的是一个 `session`；写入 JSONL 时，它会变成一行行 JSON，写入数据库时则会变成记录。这些格式转换由适配层负责。应用层只需要知道怎样存取对话，因此在应用层定义 `session_store` 接口，由适配层实现它。这样，编排流程时可以依赖接口，测试时也可以换成假存储。来源：02:13–02:34、04:10–04:56。

调用模型采用同样的安排：应用层的 `model_client` 接口规定 `generate(context, setting)` 这一能力，具体厂商协议交给适配层。视频以思考深度参数为例，说明内部统一概念如何映射到不同厂商的字段；这些字段名称是示例中的协议描述，使用时仍需核对实际 API。来源：06:34–07:29。

**归纳**：这套设计的关键是让应用层表达“流程需要什么”，让适配层决定“用什么实现”。分层的收益来自这个依赖关系，单独拆分目录并不能说明已经获得同样的可替换性。

## 3. 工具调用与审核共用对话状态，但使用不同上下文

为了让循环能够继续，系统需要把用户消息、模型回复和工具执行结果保存在同一段对话中。示例里的 `session.messages` 包含这三种消息；工具结果带有 `tool_call_id`，用来说明它对应哪次工具请求。来源：02:54–03:59。

在此基础上，作者为两类模型任务分别定义角色：

- `assistant` 根据对话生成回复或工具调用，拥有自己的指令和可用工具。
- `tool_call_reviewer` 根据对话和待审核调用生成审核结论，拥有自己的指令，不使用工具。

两者都生成 `context`，其中包括指令、工具、历史消息和输出类型；区别在于，前者要求输出 `assistant_message`，后者要求输出表示是否允许执行及拒绝原因的 `decision`。作者使用泛型表达输出类型的变化。来源：05:51–06:27、07:37–08:25。

当模型请求调用工具时，这个示例先调用 reviewer；通过后才执行工具，拒绝时则把原因作为工具结果交回模型。这样，拒绝也进入原有的反馈循环。两种角色可以配置不同模型和思考深度，作者建议 reviewer 可以考虑使用更便宜、更快的模型；`agent_service` 还持有 `max_iterations`，限制循环次数。来源：00:27–00:57、08:22–08:55。

这里的模型审核是作者选择的实现路径。视频没有给出其安全效果或成本评测，不能据此推导出所有 Agent 都需要第二个模型，也不能把审核通过理解为命令执行安全已得到保证。

## 4. 在组装根连接实现，再检查新功能会影响哪里

前面的应用流程只认识接口，系统启动时仍然需要创建具体的模型客户端、存储和其他组件，并把它们连接起来。作者把这个位置称为组装根，并用更换模型的示例说明：在兼容现有接口的情况下，可以在这里调整具体实现的选择。来源：09:24–09:56。

同样，网页和命令行只是进入应用流程的不同方式：HTTP 适配器把请求转换成对 `agent_service` 的调用，CLI 可以通过另一个适配器调用同一套应用能力。来源：09:00–09:20。

作者最后把设计过程概括为：梳理流程，建立领域概念，在应用层编排并声明接口，在适配层实现，最后组装；并留下对话分支和上下文压缩两个练习，没有提供其完整设计。来源：10:14–11:05。

**归纳**：这个例子提供了一种检查变化影响范围的方法：换模型协议时，能否主要调整适配器和组装；测流程时，能否换掉真实模型或存储；新增入口时，能否复用应用服务。它没有证明任意新功能都只需修改组装根，对话分支或压缩仍需要结合内部概念和流程继续设计。

**[00:00]** 众所周知,Agent就是个循环,看起来非常简单。但如果真要做一个Agent,要考虑的问题其实不少。如何适配多种模型,如何确保命令执行安全。以及在模型快速进化的现在,要如何设计Harness来保持可扩展性。这个视频将从零设计一个Agent后端,你不仅能了解一个Agent到底应该怎么设计。更重要的是,这套设计思路可以移植到任何系统上。首先,让我们梳理一下一个Agent后端的工作流程。
**[00:27]** 第一步,开始一个新对话,或者积蓄之前的旧对话。然后收到前端发送的用户信息,接着将指令、可用工具、历史消息等信息组织成上下文,再将上下文发送给模型,收到模型回复。如果模型的回复中有工具调用,就另外调一次模型来审核工具调用是否合理。当然,也需要另外组织一把上下文。接着,如果审核通过,就执行工具,并将执行结果,带着之前的上下文一起重新传给模型。如果审核不通过,就反会拒绝结果。重复前面的步骤三到步骤六。
**[00:57]** 直到模型的响应中,不再有工具调用,或者循环次数达到上限,就结束这种对话,将信息返回给前端。这个过程中,每条信息产生的时候,都会做持久化存储。
**[01:08]** 这个流程其实实现起来并不难,如果我们不带着任何设计去实现这个流程,大概就是一个函数复的其中一个步骤,但这样会让代码变得难以维护,又难以测试。
**[01:17]** 比如,想把使用的模型从OpenAI换成Anthropic的协议,得同时修改多个地方,又或者想要测试一下流程,却得真正调用模型。
**[01:25]** 计划前,又很慢。所以为了好维护,好测试,我们通常会将要做的是分为几层,每层都对应不同的工作性质。
**[01:34]** 首先是领域层,它用来定义系统自己的语言,比如什么是对话,什么是工具,什么是上下文。
**[01:41]** 每个系统都有自己对这些概念的理解,怎么定义这些概念,决定了这个系统会是什么样子的。
**[01:47]** 然后是应用层,将这些概念编排成完整的应用,它会调度领域层定义的各种概念,安排先做什么,后做什么,什么时候继续循环,什么时候结束,主要系到一个编排上的作用。
**[01:59]** 最后是适配层,适配层用于将系统外部的东西翻译成我们自己的语言。
**[02:06]** 我们的系统需要使用外部的东西,比如外部的存储,外部的模型,而外部对概念的定义肯定和我们不一样。
**[02:13]** 举个例子,如果要存储对话,我们的对话是一个session对象,而存到jsonl文件里是一行行的json。
**[02:20]** 存机数据库是表里一条条记录,我们需要做一个翻译的动作,才能让session顺利地在我们的系统和外部之间流动。
**[02:28]** 于是有了适配层,当我们要使用外部存储,它将我们的概念翻译成存储要用的格式。
**[02:34]** 当我们要调用外部模型,它将我们的概念翻译成需要的参数,并将模型的回复翻译成我们定义的概念。
**[02:40]** 到这里,你应该有种感觉就是适配层和应用层是为领域层而生的,的确如此,因为如何定义领域就是一个系统的本质。
**[02:49]** 接下来我们看一下都有哪些领域的概念,以及应用层和适配层要为这些概念做什么。
**[02:54]** 首先,我们需要定义对话,这是整个系统最重要的概念,因为整个系统的表现形式就是对话。

**[03:11]** ID的类型可以是字符串,然后是这次对话发送的信息messages,类型是列表。
**[03:16]** 因为信息会随着对话增长,所以我们需要一个方法来加入新的信息,于是有了append这个方法。
**[03:24]** 那么messages这个列表里面具体是什么呢?
**[03:27]** 很容易想到有用户发的user message和AI助手回复的assistant message。
**[03:31]** user message里面装文本,assistant message除了文本还会有工具调用。
**[03:36]** 工具调用,我们定一个tool call对象来包装。
**[03:40]** 拥有ID和要调用的工具名称,以及调用工具的参数。
**[03:44]** 既然对话里会记录工具调用,那调用工具的结果自然也要放入对话里。
**[03:50]** 于是我们定一个tool result对象,它需要拥有tool call ID来说明是哪次工具调用的结果,
